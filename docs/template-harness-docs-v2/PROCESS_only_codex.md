# Codex 전용 하네스 프로세스 템플릿

> 용도: 계획·구현·리뷰를 Codex만으로 수행하는 프로젝트 또는 단위 작업
> 사용: 이 문서를 작업 하네스 폴더에 복사하고, 해당 프로젝트의 `AGENTS.md`와 `docs/TECH_STACK.md`에 맞춰 경로·검증 명령을 확인한다.
> 우선순위: 사용자의 명시 요청과 프로젝트 규칙이 이 템플릿보다 우선한다.

## 1. 문서와 역할

| 단계 | 담당 | 기록 |
|---|---|---|
| 요구사항 분석·AC 정의 | Codex | `PRD.md`, `TASK_PLAN.md` |
| 구현·자체 검증 | Codex | `TASK_RESULT.md` |
| 결함 중심 리뷰·판정 | Codex의 별도 리뷰 패스 | `REVIEW.md` |

- 기존 `PROCESS.md`는 Claude Code·Codex 조합의 표준안으로 유지한다. Codex 전용으로 실행할 작업에서만 이 문서를 선택한다.
- `PRD.md`와 `TASK_PLAN.md`는 계획 단계의 기준이다. `TASK_RESULT.md`와 `REVIEW.md`는 실제 구현·검증 전에는 완료 내용으로 채우지 않는다.
- 같은 Codex 세션에서 구현과 리뷰를 모두 수행했다면 **자체 리뷰**로 표기한다. 새로운 Codex 세션을 사용한 경우에도 교차 모델 리뷰라고 표기하지 않는다.
- 기존 템플릿의 문서 머리말에 Claude Code 소유·소비 표기가 남아 있다면, Codex 전용 작업 폴더로 복사할 때 담당자를 Codex로 바꾼다. 역할 표기만 고치고 정형 항목은 유지한다.

## 2. 작업 순서

1. **범위 고정**: 현재 브랜치·작업 트리와 사용자 선행 변경을 확인한다. 제품 문서, 현재 `TASK_PLAN.md`, 프로젝트 규칙, 변경 대상 코드만 읽는다. 작업 범위와 제외 범위, 검증 가능한 AC를 확정한다.
2. **필요한 만큼 설계**: 수정할 파일과 데이터·UI 경계를 정한다. 기존 컴포넌트·상수·계약을 먼저 확인하고 중복 정의를 피한다. 정책이 모호하면 사용자가 이미 정한 내용을 우선 적용하고, 결정할 수 없는 항목만 질문 또는 리스크로 남긴다.
3. **작은 단위 구현**: 서로 의존하는 변경을 한 단위로 묶어 구현한다. 버그 수정은 재현 실패 테스트를 먼저 확인한다. 새 테스트는 행동과 실패 경로처럼 실제 위험을 검증한다.
4. **빠른 검증**: 변경한 테스트를 실행하고 프로젝트가 정한 타입·린트 빠른 게이트를 실행한다. 실패한 항목을 고친 뒤 필요한 검사만 다시 실행한다. 전체 게이트를 구현·리뷰 왕복마다 반복하지 않는다.
5. **실사용 검증**: `TASK_PLAN.md`의 AC에 맞춰 수동 또는 E2E 경로를 재현한다. UI 작업이면 대표 화면 크기와 상태를 캡처해 기준 시안과 비교한다. 시각적 목표가 수치로 주어졌다면 `TASK_PLAN.md`에 측정 항목·필수 항목·합격선을 먼저 정의하고 항목별 결과를 기록한다.
6. **결과 기록**: `TASK_RESULT.md`에 AC 자체 판정, 실행 명령과 실제 출력 요약, 재현 절차·캡처 위치, diff만으로 알 수 없는 결정과 미해결 사항을 정형 항목으로 기록한다. 실행하지 않은 검증을 통과했다고 쓰지 않는다.
7. **리뷰 패스**: 구현 설명에서 벗어나 현재 diff → AC → 검증 증거 순서로 확인한다. 기능·회귀·아키텍처·접근성·테스트 누락을 검토하고 `REVIEW.md`에 AC별 PASS/FAIL 및 Blocker/Major/Minor를 기록한다. 가능하면 구현 컨텍스트와 분리된 Codex 세션에서 검토하되 필수로 만들지 않는다.
8. **수정과 종료**: Blocker/Major는 해당 항목만 수정하고 재검토한다. Minor는 이월할 수 있다. 리뷰가 PASS하면 프로젝트가 정한 최종 통합 게이트를 커밋 직전에 실행한다. 커밋이 요청되지 않은 경우 임의로 커밋·아카이브하지 않고 최종 게이트 실행 여부를 명시한다. 커밋 후에는 프로젝트의 아카이브 규칙을 따른다.

## 3. 판정 기준

- **필수 AC는 전부 PASS**여야 한다. 목표 달성률이나 시각 유사도 점수로 기능·접근성·보안 실패를 상쇄하지 않는다.
- `TASK_PLAN.md`에 90% 같은 수치 목표가 있다면 분모, 항목별 가중치, 필수 항목, 증거 방식을 먼저 정의한다. 정의하지 않았다면 임의의 퍼센트를 보고하지 않는다. 시안 비교의 항목 점수를 자동 이미지 유사도 점수라고 표현하지 않는다.
- 리뷰 근거는 실제 diff와 재현 가능한 검증 결과다. `TASK_RESULT.md`의 주장만으로 PASS하지 않는다.
- 리뷰가 3라운드를 넘거나 같은 쟁점이 두 번 왕복하면 루프를 멈추고 사용자 판단을 요청한다.
- 전체 게이트에서 새 실패가 나면 원인을 수정하고 리뷰를 갱신한 뒤 최종 단계에서 다시 실행한다. 기존 실패와 새 실패를 구분해 보고한다.

## 4. 토큰 사용 원칙

- 관련 파일을 한 번에 찾고 필요한 범위만 읽는다. 이미 확인한 파일을 이유 없이 반복해서 읽지 않는다.
- 진행 상황에는 새로 확인한 사실·변경된 결정·막힌 사항만 남긴다. 긴 로그는 경로와 실패 요약으로 대체한다.
- 독립적인 읽기·검색은 묶어 실행한다. 수정·검증·리뷰의 의존 순서는 유지한다.
- 리뷰는 전체 구현의 재설명이 아니라 결함과 AC 미충족을 찾는 별도 패스다. 비용 절감을 이유로 필수 검증을 생략하지 않는다.

## 5. 프로젝트 적용 시 확인

- `AGENTS.md`가 여러 모델·세션 분담을 필수로 요구한다면 이 문서만 복사해서는 Codex 전용 절차가 활성화되지 않는다. 해당 작업에 Codex 전용 방식을 적용한다는 사용자 지시를 확인하고 프로젝트 지침과 문서 담당 표기를 함께 정리한다.
- 게이트 명령, 테스트 프레임워크, UI 비교 화면 크기, 커밋·아카이브 위치는 프로젝트 문서를 사용한다. 이 템플릿에 특정 저장소의 명령·티켓 번호·화면 경로를 하드코딩하지 않는다.
